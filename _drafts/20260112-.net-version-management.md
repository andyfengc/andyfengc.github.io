# Introduction
根据用途不同，在 .NET 中**存在 4 种版本概念**：

| 名称                               | 作用                            | 常见误区                                                                                                           |
| -------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------- |
| **AssemblyVersion**<br>CLR 绑定    | CLR 绑定<br>.NET 运行时用来识别程序集的强名称 | [assembly: AssemblyVersion("1.0.0.0")]<br>❌ 不应该频繁变<br>这个是“技术版本”，不是“产品版本”<br>如果程序集有依赖关系，更改这个版本必须重新编译            |
| **FileVersion**<br>人类阅读          | 文件属性<br>Windows 文件右键属性看到的版本。  | [assembly: AssemblyFileVersion("1.3.0.154")]<br>用来给人看的<br>不影响 CLR<br>建议每次构建都自增，用于排查用户手里那个 `.exe` 到底是哪天编译的。     |
| **InformationalVersion**<br>自动升级 | 显示 / 日志                       | [assembly: AssemblyInformationalVersion("1.3.0+build.154")]<br>⭐ 最重要<br>可以是任意字符串。记录Git Hash，构建号，预发布标识。用来做版本自动化 |
| **Package Version**<br>包管理       | NuGet / 发布                    | `<Version>1.3.0</Version>`<br>用于 NuGet 发布<br>遵循语义化版本 SemVer                                                    |
在 .NET 项目中，双击 `.csproj` 文件，你会发现版本号由三个核心属性控制：
- `<Version>`: 整体版本号（NuGet  package包版本）。    
- `<AssemblyVersion>`: .NET 运行时识别的版本，通常只保留主版本号（如 `1.0.0.0`），避免因版本微调导致 DLL 引用失效。    
- `<FileVersion>`: Windows 文件属性里看到的版本号。
```xml
<PropertyGroup>
  <Version>1.3.0</Version>
  <AssemblyVersion>1.3.0.0</AssemblyVersion>
  <FileVersion>1.3.0.0</FileVersion>
  <InformationalVersion>1.3.0</InformationalVersion>
</PropertyGroup>
```
只维护 `<Version>`，其余可自动派生
```xml
<PropertyGroup>
  <TargetFramework>net8.0-windows</TargetFramework>
  <VersionPrefix>1.2</VersionPrefix>
  <VersionSuffix>$([System.DateTime]::Now.ToString("yyyyMMdd-HHmm"))</VersionSuffix>
  <GenerateAssemblyInfo>true</GenerateAssemblyInfo>
</PropertyGroup>
```
这会生成类似 `1.2.20260112-0820` 的版本号，一眼就能看出程序是什么时候编译的。

每个版本号，在 .NET 中有固定格式，一个标准的版本号格式为：
```
主版本号(Major).次版本号(Minor).构建号(Build).修订号(Revision)
例如 1.2.5.100
```
- **Major (主版本号):** 发生重大重构、架构调整或不兼容的 API 更改。    
- **Minor (次版本号):** 增加了新功能，但保持向下兼容。    
- **Build (生成号):** 通常用于记录编译日期或流水线构建次数。    
- **Revision (修订号):** 修复 Bug 或微调。
# 如何管理？
在早期.NET Framework 时代：
- 手动改 `AssemblyInfo.cs`    
- 每个项目改一次    
- 发布前靠记忆   
❌ **完全不可复现**  
❌ **极易出错**
从 .NET Core 开始，实现了版本号自动化管理：
- `.csproj` 统一管理版本    
- 自动生成 AssemblyInfo    
```xml
<PropertyGroup>
  <Version>1.3.0</Version>
</PropertyGroup>
```
为了实现自动化，版本号必须满足：
1. **唯一**    
2. **可复现**    
3. **自动生成**    
4. **与源码历史绑定**
## 自动版本管理的 3 种层级
🟢 Level 1：手动版本（不推荐）
```xml
<Version>1.3.1</Version>
```
问题：
- 容易忘    
- 无法追踪
Level 2：半自动（MSBuild）
```
<Version>1.3.0</Version>
<FileVersion>1.3.0.$(BuildNumber)</FileVersion>
```
- 主版本手动    
- 构建号自动
Level 3：全自动（最佳实践）
- Git 是唯一版本源    
- 构建时自动计算
代表工具：
- Nerdbank.GitVersioning ⭐    
- GitVersion

.NET 的版本管理，本质是：  
用 Git 表示“历史”，用构建系统“计算版本”，而不是靠人去记。
## 具体实践
### 方案 A：手动模式（入门）
在你的 .csproj 中直接写死：
```xml
<PropertyGroup>
  <Version>1.0.5</Version>
  <FileVersion>1.0.5.1234</FileVersion>
</PropertyGroup>
```
### 方案 B：日期自动生成（进阶）
利用 MSBuild 的内置函数，让版本号随编译时间变动。这在开发阶段非常有用，不需要手动去改。
```xml
<PropertyGroup>
  <VersionPrefix>1.2.0</VersionPrefix>
  <VersionSuffix>$([System.DateTime]::Now.ToString("yyyyMMdd-HHmm"))</VersionSuffix>
  <Version>$(VersionPrefix)-$(VersionSuffix)</Version>
</PropertyGroup>
```
### 方案 C：GitVersion / MinVer（最佳实践）
**这是目前 .NET 社区的行业标准。** 它的逻辑是：**代码里不写版本号，版本由 Git 标签决定。**
1. **原理：** 工具扫描你的 Git 历史。如果你打了一个 Tag 叫 `v1.1.0`，它会自动把程序版本设为 `1.1.0`。如果你又提交了 3 次，它会自动设为 `1.1.1-preview.3`。    
2. **配置：**    
    - 安装 NuGet 包 `GitVersion.MsBuild`。        
    - 删除 `.csproj` 里的所有 `<Version>` 标签。        
    - **好处：** 保证了版本号与代码版本库（Git）的绝对统一。
### 利用 Git 标签自动生成 (GitVersion)
这是专业团队最常用的方案。使用 **GitVersion** 工具，它会根据你的 Git Tag 和分支自动计算语义化版本号（SemVer）。
1. **安装：** `dotnet tool install --global GitVersion.Tool`    
2. **原理：** * 你打一个 Tag 叫 `v1.1.0`。    
    - 你在主分支提交了两次，它会自动生成 `1.1.2`。        
    - 你开了一个 feature 分支，它会自动生成 `1.2.0-alpha.1`。        
3. **集成：** 在 GitHub Actions 或 GitLab CI 中直接调用，它可以自动修改 `.csproj` 里的版本号再进行编译。
## Nerdbank.GitVersioning（NBGV）
安装：
`dotnet add package Nerdbank.GitVersioning`
version.json：
`{   "version": "1.3" }`
自动生成：
`main:    1.3.0 dev:     1.3.1-alpha.12 tag:     1.3.0`
# 桌面程序升级流程
## 程序自动更新原理（二进制文件更新）
WPF 本身不内置更新机制，建议采用“主程序 + 外置启动器（Launcher/Updater）”的模式。
```
MyApp.Launcher.exe     ← 永远不自升级
MyApp.exe              ← 业务程序
update.json            ← 版本信息
packages/
  └─ MyApp.1.2.3.zip   ← 新版本包
```
升级完整流程
```
启动 Launcher
  ↓
读取本地 version.json
  ↓
请求服务器 update.json
  ↓
版本对比
  ↓
有新版本？
  ├─ 否 → 启动 MyApp.exe
  └─ 是
      ↓
下载 zip
      ↓
校验 hash
      ↓
解压覆盖
      ↓
启动 MyApp.exe --migrate
      ↓
退出 Launcher
```
### 为什么一定要 Launcher？
- **运行中的 exe 不能覆盖自己**    
- WPF 主程序一旦加载 DLL 就会锁文件    
- 数据库 Migration 必须在**新版本代码下运行**
- Launcher 负责：下载 → 校验 → 解压 → 启动 → 退出
- **Velopack (原 Squirrel.Windows 的继任者)：** 目前 .NET 生态中最好用的安装与更新框架，处理文件替换非常丝滑。
- **Polly：** 用于处理下载更新时的断线重连。
### 更新流程
1. **检测到新版本：** 弹出提示框告知用户。    
2. **启动更新器：** 主程序关闭，启动一个独立的 `Updater.exe`。    
3. **下载与解压：** 更新器下载 ZIP 包并覆盖主程序目录。    
4. **重启：** 更新器完成工作后，重新拉起主程序。
## 检查更新. 
本地版本（version.json）
```json
{
  "appVersion": "1.2.0",
  "dbVersion": "20240101"
}
```
在主程序启动时，请求一个远程 JSON 文件, 服务端 update.json：
```json

  "Url": "https://cdn.xxx.com/update_v1.2.0.zip",

}
```
## Launcher 核心实现（关键代码）
版本对比
```csharp
if (Version.Parse(remote.appVersion) > Version.Parse(local.appVersion))
{
    DownloadAndUpdate();
}

void DownloadAndUpdate(){
	ZipFile.ExtractToDirectory(zipPath, appDir, overwriteFiles: true);
}
```
**注意**
- 解压前关闭主程序    
- 排除 `user.config`    
- 排除数据库文件（如果是本地）


```csharp
[STAThread]

{
    if (args.Contains("--migrate"))
    {
        RunMigration();
    }

    RunWpf();
}
```

```csharp

{
```

- 检查 `__EFMigrationsHistory`    
- 自动执行缺失的 Migration    
- 保证幂等
## 数据库迁移 Migration 版本控制的最佳实践流程(数据库配置版)：
对于本地数据库（如 SQLite），迁移必须在**主程序启动后的第一时间**、在执行任何业务逻辑之前完成。
- 使用**EF Core Migrations：** 处理数据库结构演变。
- 数据库升级必须由“新版本程序”执行，也就是说，自动升级，必须先升级完主程序再升级数据库
### 数据库准备
**记录版本：** 在数据库中创建一个 `SystemInfo` 表，记录当前已完成迁移的 `AppVersion`。

| **Key**      | **Value**                     | **说明**       |
| ------------ | ----------------------------- | ------------ |
| `AppVersion` | `1.2.5`                       | 当前安装的可执行文件版本 |
| `DbVersion`  | `20240112_AddAttachmentTable` | 最后一次执行的迁移名称  |
| UpdatedAt    |                               |              |
### **启动检查：** 
在启动入口，如 `App.xaml.cs` 中，获取当前编译的版本号：
```csharp
var currentAppVersion = Assembly.GetExecutingAssembly().GetName().Version;
```
### 对比数据库中的 AppVersion。
如果当前代码版本 > 数据库记录的版本，说明是更新后的第一次运行，执行迁移 dbContext.Database.Migrate()。
在你的 `App.xaml.cs` 的 `OnStartup` 方法中，注入迁移代码：
```csharp
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    using (var context = new MyDbContext())
    {
        // 这行代码会自动检测数据库版本
        // 如果数据库版本低于代码版本，会执行所有缺失的 Migration
        context.Database.Migrate();
    }
}
```
### 迁移成功后，更新数据库中的 AppVersion 字段。
### 关键点与坑点处理
1. 迁移失败的回滚
如果 `Database.Migrate()` 报错（例如你之前的“外键约束失败”），程序会直接崩溃。 **修复方案：** 增加异常捕获和备份机制。
- 在执行迁移前，**先备份 `.db` 文件**。    
- 如果迁移失败，弹出错误提示并还原备份，防止用户数据损坏。  
2. SQLite 的局限性
SQLite 对某些 Schema 修改（如重命名列、删除外键）支持有限。
- **技巧：** 在 EF Core 迁移脚本中，EF 会自动创建一个临时表，把数据导进去，删掉旧表再重命名。确保迁移期间没有其他进程占用数据库文件。    
3. 多客户端同步（如果使用远程数据库）
如果你的 WPF 是连接中心化 SQL Server：
- **版本锁：** 数据库中可以建一个 `SystemSettings` 表记录当前 `DbVersion`。    
- 第一个升级的客户端负责执行 Migration，其他低版本客户端检测到版本不匹配时，强制要求用户下载更新，禁止进入系统，防止旧代码写坏新结构。
